What is a Backend?

Every application has two sides — this is the half users never see.

When you open a web or mobile app, what you see is the frontend — buttons, forms, screens. But when you press "Sign In", something behind the scenes validates your password, looks up your account, and sends your data back. That invisible layer is the backend.

FrontendBackend
Runs in the browser or phoneRuns on a server
Shows data to the userStores and processes data
HTML, CSS, JavaScript / React NativeNode.js, Python, Go, Java…
Can be seen and modified by usersUsers cannot access it directly
Stateless (data reloaded per page)Stateful (data persists in database)

What a backend does

  • Receives requests from clients (browser, mobile app, other servers)
  • Validates and processes the data — is this user allowed? is the input valid?
  • Reads/writes the database — look up members, create payments, save settings
  • Calls external services — payment providers, email services, SMS
  • Sends a response back — usually JSON data
💡
This course's stack

Node.js (runtime) + Express (HTTP framework) + PostgreSQL (database) + Redis (cache/queue). This is one of the most common production stacks in the world and exactly what runs this app.

How the Web Works

The full journey of a request — from the user's tap to the database and back.

User taps "View Members" in the admin app ↓ Browser/App sends HTTP GET https://api.myfiti.fit/api/members ↓ (travels over the internet) Caddy reverse proxy receives request, forwards to Node.js on port 4000 ↓ Express matches route GET /api/members, runs middleware chain ↓ Auth MW verifies JWT token — is this user logged in? ↓ Tenant MW resolves gym slug → finds which database schema to use ↓ Route handler runs: SELECT * FROM members WHERE status = 'active' ↓ PostgreSQL executes query, returns rows ↓ Route handler formats rows as JSON, sends response ↓ (travels back over internet) Browser/App receives JSON, renders the member list

Every API call follows this same path. Your job as a backend engineer is to build each layer correctly.

Node.js Basics

Node.js lets you run JavaScript on a server — not just in the browser.

Before Node.js existed, JavaScript only ran in browsers. Node.js is a runtime built on Chrome's V8 engine that executes JavaScript on your machine or server.

Key characteristics

PropertyWhat it means
Single-threadedOne thread handles all requests — no parallel execution
Non-blocking I/OWhile waiting for DB/file/network, handles other requests instead of sleeping
Event loopThe mechanism that manages async operations — "do this, when done call me back"
npm / pnpmPackage managers — install libraries like Express, Drizzle, etc.

async/await — the foundation of backend Node.js

// Almost everything in Node.js is async — it takes time and doesn't block

// BAD — this "blocks" — nothing else can run while sleeping
function sleep(ms) {
  const start = Date.now()
  while (Date.now() - start < ms) {} // busy loop — terrible
}

// GOOD — async: gives control back to Node while waiting
async function getMembers() {
  const rows = await db.query('SELECT * FROM members')
  // while db is running the query, Node handles other requests
  return rows
}

// async functions always return a Promise
// await pauses execution of THIS function until the promise resolves
// but does NOT block the entire server

CommonJS vs ES Modules

// CommonJS (older — .js files with "type":"commonjs" in package.json)
const express = require('express')
module.exports = { router }

// ES Modules (modern — .js files with "type":"module" or .mjs extension)

export { router }

// This project uses ES Modules ("type":"module" in package.json)

Routes & Handlers

Routes map URL patterns to functions. Every API endpoint is a route.

// Route syntax: app.METHOD(PATH, HANDLER)
// METHOD = get | post | patch | put | delete
// PATH   = string or pattern with :params
// HANDLER = function(req, res) { ... }

// GET — no body, returns a list
app.get('/members', (req, res) => {
  res.json({ members: [] })
})

// POST — receives a body, creates something
app.post('/members', (req, res) => {
  const { name, email } = req.body      // from JSON body
  // ... save to database ...
  res.status(201).json({ member: { id: 'uuid', name, email } })
})

// Path parameter — :id is a variable
app.get('/members/:id', (req, res) => {
  const { id } = req.params             // from URL
  res.json({ member: { id } })
})

// PATCH — partial update
app.patch('/members/:id', (req, res) => {
  const { id }    = req.params
  const { phone } = req.body
  res.json({ ok: true })
})

// DELETE
app.delete('/members/:id', (req, res) => {
  res.status(204).send()   // 204 = No Content (deleted)
})

Organising routes — Express Router

// routes/members.js — separate file for member routes
import { Router } from 'express'

export const membersRouter = Router()

membersRouter.get('/',     listMembers)
membersRouter.post('/',    createMember)
membersRouter.get('/:id', getMember)
membersRouter.patch('/:id', updateMember)

// index.js — mount the router under /members
import { membersRouter } from './routes/members.js'
app.use('/members', membersRouter)

// Now: GET /members → listMembers
//      GET /members/:id → getMember

Request & Response Objects

The two objects every handler receives — know every part of them.

The Request (req)

// req contains everything the client sent
app.post('/members/:id/subscribe', (req, res) => {

  req.params.id          // path parameter:  /members/b8160866 → "b8160866"
  req.query.status       // query param:     ?status=active → "active"
  req.body.plan_id       // JSON body field: { "plan_id": "uuid" }
  req.headers['authorization']  // header:         "Bearer eyJ..."
  req.headers['x-tenant-slug']  // custom header:  "korafit"
  req.method             // HTTP method:     "POST"
  req.path               // URL path:        "/members/b8160866/subscribe"
  req.ip                 // client IP:       "41.189.xxx.xxx"

  // Properties set by middleware (you'll add these):
  req.user               // set by auth middleware
  req.tenant             // set by tenant middleware
})

The Response (res)

// res is how you send the response back

res.json({ ok: true })              // send JSON (sets Content-Type automatically)
res.status(201).json({ member })    // set status code + send JSON
res.status(204).send()             // no body (used for DELETE)
res.status(400).json({ error: 'Email is required' })
res.setHeader('X-Request-Id', uuid) // set a response header
res.redirect('https://example.com') // 302 redirect

Middleware

The most powerful concept in Express — functions that run before your route handlers.

A middleware is a function with the signature (req, res, next). It can read/modify the request, send a response early (to reject), or call next() to pass to the next middleware.

The middleware pipeline

Request → [Helmet] → [CORS] → [Morgan/Logger] → [JSON Parser] → [Rate Limiter] → [Auth MW] → [Tenant MW] → [Route Handler] ← your business logic lives here → [Error Handler] ← catches any thrown errors → Response sent to client

Writing your own middleware

// A middleware logs every request
function requestLogger(req, res, next) {
  console.log(`${req.method} ${req.path} — ${new Date().toISOString()}`)
  next()   // MUST call next() or the request hangs forever
}

app.use(requestLogger)   // apply globally

// Apply to a specific route only
app.get('/members', requestLogger, listMembers)

Middleware that rejects requests (auth guard)

function requireAuth(req, res, next) {
  const header = req.headers['authorization']

  if (!header?.startsWith('Bearer ')) {
    return res.status(401).json({ error: 'No token provided' })
    // does NOT call next() — request stops here
  }

  const token = header.slice(7)  // remove "Bearer "

  try {
    const payload = jwt.verify(token, process.env.JWT_SECRET)
    req.user = payload   // attach to req so handlers can use it
    next()               // token valid — continue
  } catch {
    res.status(401).json({ error: 'Invalid or expired token' })
  }
}

// Protect all routes under /api
app.use('/api', requireAuth)

The next(error) pattern

// Passing an error to next() skips to the error handler
async function listMembers(req, res, next) {
  try {
    const members = await db.query('SELECT * FROM members')
    res.json({ members })
  } catch (err) {
    next(err)   // → goes to errorHandler middleware
  }
}

Middleware order matters

// WRONG order — rate limiter after auth means unauthenticated requests aren't limited
app.use(requireAuth)
app.use(rateLimiter)   ← too late

// CORRECT order
app.use(helmet())         // 1. Security headers first
app.use(cors(config))     // 2. CORS — before any route handling
app.use(morgan('dev'))    // 3. Logging — log everything
app.use(express.json())   // 4. Body parsing — before handlers read req.body
app.use(rateLimiter)      // 5. Rate limit — before auth so bots are stopped early
app.use(requireAuth)      // 6. Auth — after body parsing, before routes
app.use(router)           // 7. Routes — your business logic
app.use(errorHandler)     // 8. Error handler — must be LAST

Databases — Introduction

Where data actually lives — and why you can't just use a file.

A database is a program that stores and retrieves data reliably. It handles concurrent access (100 users writing at once), data integrity (no partial writes), and fast queries.

SQL vs NoSQL

SQL (Relational)NoSQL (Document)
ExamplesPostgreSQL, MySQL, SQLiteMongoDB, DynamoDB, Firestore
Data formatTables with rows and columns — like a spreadsheetDocuments (JSON objects) — flexible schema
RelationshipsForeign keys — strict, enforced by DBEmbed or reference — no enforcement
ACIDFull ACID transactionsVaries — most support limited transactions
Best forFinancial data, user accounts, anything relationalFlexible schemas, logs, analytics, caches
This appPostgreSQL (Neon) — primary data storeRedis — cache and job queue only

ACID — why it matters for payments

PropertyGuaranteeExample
AtomicAll-or-nothing: either every step succeeds or none doDeduct wallet balance AND create payment — not one without the other
ConsistentData always moves from one valid state to anotherBalance can never go below 0
IsolatedConcurrent transactions don't interfere with each otherTwo renewal requests don't double-activate the same subscription
DurableCommitted data survives crashes and restartsPayment confirmed even if server restarts immediately after

SQL Basics

The language you use to talk to a relational database — know it, it never goes away.

The four fundamental operations (CRUD)

── CREATE (INSERT) ──────────────────────────────────────────
INSERT INTO members (id, name, email, status, created_at)
VALUES ('b8160866-...', 'Alice Mbah', 'alice@example.cm', 'active', NOW());

── READ (SELECT) ────────────────────────────────────────────
-- All members
SELECT * FROM members;

-- Specific columns, with filter
SELECT id, name, email FROM members WHERE status = 'active';

-- With sorting and limit
SELECT * FROM members ORDER BY created_at DESC LIMIT 20 OFFSET 0;

-- Search (case-insensitive)
SELECT * FROM members WHERE name ILIKE '%alice%';

── UPDATE ───────────────────────────────────────────────────
UPDATE members
SET    status = 'expired', updated_at = NOW()
WHERE  id = 'b8160866-...';

── DELETE ───────────────────────────────────────────────────
DELETE FROM members WHERE id = 'b8160866-...';

JOINs — combining tables

-- Get each member with their current subscription plan name
SELECT
  m.name,
  m.email,
  p.name  AS plan_name,
  s.expires_at
FROM members m
INNER JOIN subscriptions s ON s.member_id = m.id AND s.status = 'active'
INNER JOIN plans        p ON p.id = s.plan_id
WHERE m.status = 'active'
ORDER BY s.expires_at ASC;

Aggregations

-- Revenue by payment method for September 2026
SELECT
  method,
  COUNT(*)      AS payment_count,
  SUM(amount)   AS total_revenue
FROM payments
WHERE status     = 'completed'
  AND paid_at   >= '2026-09-01'
  AND paid_at    < '2026-10-01'
GROUP BY method
ORDER BY total_revenue DESC;

Table design example

-- Members table
CREATE TABLE members (
  id          UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
  name        TEXT        NOT NULL,
  email       TEXT        NOT NULL UNIQUE,
  phone       TEXT,
  status      TEXT        NOT NULL DEFAULT 'pending',
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Subscriptions linked to members
CREATE TABLE subscriptions (
  id          UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
  member_id   UUID        NOT NULL REFERENCES members(id) ON DELETE CASCADE,
  plan_id     UUID        NOT NULL REFERENCES plans(id),
  status      TEXT        NOT NULL DEFAULT 'pending',
  starts_at   TIMESTAMPTZ NOT NULL,
  expires_at  TIMESTAMPTZ NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Index for fast lookup by member
CREATE INDEX idx_subscriptions_member_id ON subscriptions(member_id);
CREATE INDEX idx_members_email           ON members(email);

Connecting Express to PostgreSQL

Using the pg library to query your database from a Node.js server.

npm install pg
npm install @types/pg   # if using TypeScript

Creating a connection pool

// db/client.ts
import { Pool } from 'pg'

// A pool keeps multiple connections open, reuses them across requests
export const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  max:              10,   // max 10 simultaneous connections
  idleTimeoutMillis: 30000,
  connectionTimeoutMillis: 2000,
})

// Helper for parameterised queries
export async function query<T = Record<string, unknown>>(
  sql: string,
  params?: unknown[]
) {
  const { rows } = await pool.query<T>(sql, params)
  return rows
}

Using it in a route handler

// routes/members.ts
import { query } from '../db/client.js'

export async function listMembers(req, res, next) {
  try {
    const { status, search, page = 1, limit = 20 } = req.query
    const offset = (page - 1) * limit

    const rows = await query(
      `SELECT id, name, email, status, created_at
         FROM members
        WHERE ($1::text IS NULL OR status = $1)
          AND ($2::text IS NULL OR name ILIKE '%' || $2 || '%')
        ORDER BY created_at DESC
        LIMIT $3 OFFSET $4`,
      [status ?? null, search ?? null, limit, offset]
    )

    const [{ total }] = await query('SELECT COUNT(*) AS total FROM members')

    res.json({ members: rows, total: Number(total.total), page, limit })
  } catch (err) {
    next(err)
  }
}

export async function createMember(req, res, next) {
  try {
    const { name, email } = req.body

    // $1, $2 = parameterised — NEVER string-concatenate user input into SQL
    const [member] = await query(
      `INSERT INTO members (name, email)
       VALUES ($1, $2)
       RETURNING id, name, email, status, created_at`,
      [name, email]
    )

    res.status(201).json({ member })
  } catch (err) {
    if (err.code === '23505') {  // unique violation
      return res.status(409).json({ error: 'Email already registered' })
    }
    next(err)
  }
}
🔴
Always use parameterised queries — never string concatenation

SQL injection is the #1 database attack. query(`SELECT * FROM members WHERE email = '${email}'`) lets an attacker set email to ' OR '1'='1 and dump your entire database. The $1, $2 parameter syntax prevents this completely.

REST API Design

The conventions that make your API predictable and easy to use.

REST (Representational State Transfer) is a set of conventions for designing HTTP APIs. A well-designed REST API feels obvious — developers know what to expect.

Resource naming rules

RuleWrongCorrect
Use nouns, not verbs/getMembers, /createMember/members
Use plural nouns/member/members
Use lowercase with hyphens/DayPass, /day_pass/day-passes
Nested resources for relationships/getMemberSubscriptions?id=123/members/123/subscriptions
Use HTTP method for the actionPOST /deleteMembersDELETE /members/123

Standard CRUD mapping

// The 5 standard REST operations for a resource
GET    /members           → list (paginated)
POST   /members           → create one
GET    /members/:id       → get one
PATCH  /members/:id       → update one (partial)
DELETE /members/:id       → delete one

// Actions that don't fit CRUD — use POST to a sub-resource
POST   /members/:id/confirm-payment  → trigger an action
POST   /members/:id/resend-welcome   → trigger an action
POST   /auth/logout                  → trigger an action

Response consistency

// Always wrap in a named key — not a bare array
{ "members": [...], "total": 87 }   ✓ good
[...]                               ✗ bad — can't add metadata later

// Error responses always have "error" key
{ "error": "Email already registered." }

// Created resources return the full object
{ "member": { "id": "...", "name": "...", "status": "pending" } }

Validation with Zod

Never trust user input — always validate before touching the database.

Zod is a TypeScript-first schema library. You define what valid data looks like, and Zod checks incoming requests against it.

npm install zod
import { z } from 'zod'

// 1. Define the schema
const createMemberSchema = z.object({
  name:           z.string().min(2).max(100),
  email:          z.string().email(),
  phone:          z.string().optional(),
  gender:         z.enum(['male', 'female', 'other']).optional(),
  plan_id:        z.string().uuid().optional(),
  payment_method: z.enum(['cash', 'mobile_money', 'wallet']).optional(),
})

// 2. Use in route handler
export async function createMember(req, res, next) {
  const result = createMemberSchema.safeParse(req.body)

  if (!result.success) {
    return res.status(400).json({
      error:  'Validation failed',
      issues: result.error.flatten().fieldErrors,
    })
    // e.g. { "issues": { "email": ["Invalid email"] } }
  }

  const { name, email, phone } = result.data  // type-safe, guaranteed valid
  // ... proceed with DB insert
}

// 3. Reusable validation middleware
function validate(schema) {
  return (req, res, next) => {
    const result = schema.safeParse(req.body)
    if (!result.success) {
      return res.status(400).json({ error: result.error.flatten().fieldErrors })
    }
    req.body = result.data   // replace with cleaned/coerced data
    next()
  }
}

router.post('/members', validate(createMemberSchema), createMember)

Authentication (JWT)

How to prove who a user is — and keep them logged in across requests.

HTTP is stateless — the server doesn't remember who sent the last request. JWTs (JSON Web Tokens) solve this: after login, the server gives the client a signed token; the client sends it with every request.

JWT anatomy

// A JWT has 3 base64-encoded parts separated by dots:
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9   ← header (algorithm)
.eyJ1c2VySWQiOiJiODE2MDg2Ni4uLiIsInJvbGUiOiJvd25lciIsImlhdCI6MTcyNTI2NDAwMH0=   ← payload (your data)
.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c   ← signature (proves it's unmodified)

// Decoded payload:
{
  "userId": "b8160866-985c-4e78-8fda-d1b979a4ed3e",
  "role":   "owner",
  "tenantId": "tenant-uuid",
  "iat":    1725264000,   // issued at (Unix timestamp)
  "exp":    1725350400    // expires at (24 hours later)
}

Login flow — generate a JWT

npm install jsonwebtoken bcrypt
import jwt    from 'jsonwebtoken'
import bcrypt from 'bcrypt'

export async function login(req, res, next) {
  try {
    const { email, password } = req.body

    // 1. Find user
    const [user] = await query(
      'SELECT id, email, password_hash, role, tenant_id FROM owners WHERE email = $1',
      [email.toLowerCase()]
    )
    if (!user) return res.status(401).json({ error: 'Invalid credentials' })

    // 2. Compare password
    const valid = await bcrypt.compare(password, user.password_hash)
    if (!valid) return res.status(401).json({ error: 'Invalid credentials' })

    // 3. Sign token — never put sensitive data in payload (it's base64, readable)
    const token = jwt.sign(
      { userId: user.id, role: user.role, tenantId: user.tenant_id },
      process.env.JWT_SECRET,
      { expiresIn: '24h' }
    )

    res.json({ token, user: { email: user.email, role: user.role } })
  } catch (err) { next(err) }
}

// Auth middleware — verify on every protected request
export function requireAuth(req, res, next) {
  const header = req.headers.authorization
  if (!header?.startsWith('Bearer '))
    return res.status(401).json({ error: 'No token' })

  try {
    req.user = jwt.verify(header.slice(7), process.env.JWT_SECRET)
    next()
  } catch {
    res.status(401).json({ error: 'Invalid or expired token' })
  }
}
⚠️
JWT_SECRET must be long and random

Generate with: node -e "console.log(require('crypto').randomBytes(64).toString('hex'))". Store only in environment variables — never in code or git.

Password Hashing

You must never store passwords in plain text — ever.

Hashing is a one-way transformation. You hash the password when storing, and hash the login attempt and compare — never reversing it.

import bcrypt from 'bcrypt'

// On registration — hash before INSERT
const ROUNDS = 12  // higher = slower = harder to brute-force. 10-12 is good
const hash = await bcrypt.hash(password, ROUNDS)
// hash looks like: $2b$12$eUDT.YM1w...

// INSERT INTO owners (email, password_hash) VALUES ($1, $2)
await query('INSERT INTO owners (email, password_hash) VALUES ($1, $2)', [email, hash])

// On login — compare, never decrypt

Error Handling

A global error handler prevents crashes from leaking stack traces to users.

// middleware/error.ts
export function errorHandler(err, req, res, next) {
  // Log internally — full details for debugging
  console.error(`[ERROR] ${req.method} ${req.path}`, err)

  // Known operational errors — user-safe messages
  if (err.code === '23505')   // PostgreSQL unique violation
    return res.status(409).json({ error: 'Already exists.' })

  if (err.code === '23503')   // Foreign key violation
    return res.status(400).json({ error: 'Referenced record not found.' })

  if (err.name === 'ZodError')
    return res.status(400).json({ error: err.flatten().fieldErrors })

  // Unknown errors — don't expose internals
  res.status(500).json({ error: 'Internal server error.' })
}

// MUST be registered last, after all routes:
app.use(errorHandler)

// In route handlers — always wrap async code:
async function myHandler(req, res, next) {
  try {
    // ... code ...
  } catch (err) {
    next(err)  // → error handler picks it up
  }
}

// Or wrap handlers automatically:

ORM — Drizzle

Write type-safe database queries in TypeScript instead of raw SQL strings.

An ORM (Object-Relational Mapper) lets you define your database schema in code and query it using TypeScript — with full autocomplete and compile-time errors for wrong column names.

npm install drizzle-orm @neondatabase/serverless
npm install -D drizzle-kit

Define schema

// db/schema.ts
import { pgTable, text, uuid, timestamp } from 'drizzle-orm/pg-core'

export const members = pgTable('members', {
  id:         uuid('id').primaryKey().defaultRandom(),
  name:       text('name').notNull(),
  email:      text('email').notNull().unique(),
  phone:      text('phone'),
  status:     text('status').notNull().default('pending'),
  createdAt:  timestamp('created_at', { withTimezone: true }).defaultNow(),
})

export const subscriptions = pgTable('subscriptions', {
  id:        uuid('id').primaryKey().defaultRandom(),
  memberId:  uuid('member_id').notNull().references(() => members.id),
  status:    text('status').notNull().default('pending'),
  expiresAt: timestamp('expires_at', { withTimezone: true }).notNull(),
})

Query with Drizzle

import { db }     from './db/client.js'
import { members } from './db/schema.js'
import { eq, ilike, and } from 'drizzle-orm'

// SELECT — fully typed results
const rows = await db
  .select()
  .from(members)
  .where(and(
    eq(members.status, 'active'),
    ilike(members.name, '%alice%')
  ))
  .limit(20)
  .offset(0)

// INSERT — returns inserted row
const [member] = await db
  .insert(members)
  .values({ name: 'Alice', email: 'alice@example.cm' })
  .returning()

// UPDATE
await db
  .update(members)
  .set({ status: 'active' })
  .where(eq(members.id, memberId))

// DELETE
await db.delete(members).where(eq(members.id, memberId))

Database Patterns

Transactions, connection pooling, and query optimisation for production databases.

Transactions — multiple queries as one atomic unit

// WRONG — if the second query fails, the first already ran (inconsistent state)
await query('UPDATE wallets SET balance = balance - $1 WHERE member_id = $2', [amount, memberId])
await query('INSERT INTO wallet_transactions (...) VALUES (...)', [...])

// CORRECT — transaction wraps both: either both run, or neither does
const client = await pool.connect()
try {
  await client.query('BEGIN')

  await client.query(
    'UPDATE wallets SET balance = balance - $1 WHERE member_id = $2 AND balance >= $1',
    [amount, memberId]
  )
  // If this fails (not enough balance), the UPDATE above is rolled back

  await client.query(
    'INSERT INTO wallet_transactions (member_id, amount, type) VALUES ($1, $2, $3)',
    [memberId, -amount, 'debit']
  )

  await client.query('COMMIT')
} catch (err) {
  await client.query('ROLLBACK')
  throw err
} finally {
  client.release()   // always return connection to pool
}

Indexes — make queries fast

-- Without index: full table scan = reads every row
SELECT * FROM members WHERE email = 'alice@example.cm';   ← O(n) — slow at scale

-- Add an index: PostgreSQL jumps directly to the row
CREATE INDEX idx_members_email ON members(email);         ← O(log n) — fast

-- Index every column you filter on frequently:
CREATE INDEX idx_members_status        ON members(status);
CREATE INDEX idx_subscriptions_member  ON subscriptions(member_id);
CREATE INDEX idx_payments_created_at   ON payments(created_at DESC);

N+1 query problem — the most common performance bug

// BAD — N+1: 1 query to get members + 1 per member = 101 queries for 100 members
const members = await query('SELECT * FROM members')
for (const member of members) {
  member.subscription = await query(   // ← query inside loop
    'SELECT * FROM subscriptions WHERE member_id = $1', [member.id]
  )
}

// GOOD — 1 JOIN query gets everything
const rows = await query(`
  SELECT m.*, s.status AS sub_status, s.expires_at
  FROM members m
  LEFT JOIN subscriptions s
    ON s.member_id = m.id AND s.status IN ('active','pending','grace_period')
`)

Rate Limiting

Preventing abuse by limiting how many requests a client can make in a time window.

Without rate limiting, anyone can flood your API with millions of requests, crash your server, or brute-force passwords.

npm install @upstash/ratelimit @upstash/redis
// middleware/rate-limit.ts
import { Ratelimit }   from '@upstash/ratelimit'
import { Redis }       from '@upstash/redis'

const redis     = Redis.fromEnv()
const ratelimit = new Ratelimit({
  redis,
  limiter: Ratelimit.slidingWindow(100, '1 m'),  // 100 requests per minute per IP
})

export async function rateLimitApi(req, res, next) {
  const ip       = req.ip ?? 'unknown'
  const { success, remaining, reset } = await ratelimit.limit(ip)

  res.setHeader('X-RateLimit-Remaining', remaining)
  res.setHeader('X-RateLimit-Reset', reset)

  if (!success) {
    return res.status(429).json({ error: 'Too many requests. Try again in a minute.' })
  }
  next()
}

// Stricter limit for auth endpoints (prevent brute-force)
const authLimiter = new Ratelimit({
  redis,
  limiter: Ratelimit.slidingWindow(5, '1 m'),   // only 5 logins per minute
})

// Apply rate limits:
app.use('/api',        rateLimitApi)
app.post('/auth/login', authRateLimiter, loginHandler)

CORS & Helmet

Browser security headers that prevent entire classes of attacks.

CORS — Cross-Origin Resource Sharing

Browsers block JavaScript from calling APIs on a different domain unless the server explicitly allows it. CORS headers tell the browser which origins are allowed.

import cors from 'cors'

app.use(cors({
  origin:         process.env.CORS_ORIGIN ?? 'http://localhost:3000',
  methods:        ['GET', 'POST', 'PATCH', 'PUT', 'DELETE', 'OPTIONS'],
  allowedHeaders: ['Content-Type', 'Authorization', 'X-Tenant-Slug'],
  credentials:    true,   // allow cookies to be sent cross-origin
  maxAge:         86400,  // browsers cache preflight for 24h
}))

// CORS_ORIGIN in production = "https://app.myfiti.fit"
// NEVER use '*' with credentials: true

Helmet — security response headers

import helmet from 'helmet'

app.use(helmet())
// Sets these headers automatically:
//   Content-Security-Policy    — prevents XSS by restricting script sources
//   X-Frame-Options: DENY      — prevents clickjacking (page in an iframe)
//   X-Content-Type-Options     — prevents MIME sniffing
//   Strict-Transport-Security  — forces HTTPS
//   Referrer-Policy            — controls what URL is sent in Referer header

// Relax CSP for a specific route (e.g. API docs that load CDN scripts):
app.use('/api/docs', (_req, res, next) => {
  res.setHeader('Content-Security-Policy',
    "default-src 'self'; script-src 'self' 'unsafe-inline' https://cdn.jsdelivr.net;")
  next()
})

Background Jobs — BullMQ

Running tasks asynchronously so your API responds instantly while heavy work happens in the background.

Some operations are too slow for a request/response cycle: sending emails, generating PDFs, processing webhooks, running daily crons. Background jobs put these on a queue and process them asynchronously.

npm install bullmq ioredis

Queue + Worker pattern

// jobs/email.queue.ts — the queue (adds jobs)
import { Queue } from 'bullmq'
import IORedis   from 'ioredis'

const connection  = new IORedis(process.env.REDIS_URL, { maxRetriesPerRequest: null })
export const emailQueue = new Queue('emails', { connection })

// Add a job — returns immediately
await emailQueue.add('welcome-email', {
  to:     'alice@example.cm',
  name:   'Alice Mbah',
  gymName: 'Kora Fit',
}, {
  attempts: 3,       // retry up to 3 times on failure
  backoff: { type: 'exponential', delay: 5000 }  // wait 5s, 10s, 20s between retries
})
// jobs/email.worker.ts — the worker (processes jobs)
import { Worker } from 'bullmq'

const worker = new Worker('emails', async (job) => {
  if (job.name === 'welcome-email') {
    await sendWelcomeEmail(job.data)
    console.log(`Sent welcome email to ${job.data.to}`)
  }
}, { connection })

worker.on('failed', (job, err) => {
  console.error(`Job ${job.id} failed:`, err.message)
})

// Workers run in a separate process or in the same server
// They process jobs one at a time (or concurrently with { concurrency: 5 })

Scheduled cron jobs with BullMQ

// Run subscription expiry check every day at midnight
await emailQueue.add(
  'check-expiring-subscriptions',
  {},
  {
    repeat: { cron: '0 0 * * *' },  // cron syntax: min hour day month weekday
    jobId: 'subscription-cron',      // stable ID prevents duplicate crons on restart
  }

Caching — Redis

Store expensive computation results in memory so you don't repeat them.

Redis is an in-memory key-value store. Reading from Redis takes ~1ms; reading from PostgreSQL over a network can take 10–100ms. For data that doesn't change often, cache it.

npm install ioredis
import IORedis from 'ioredis'
const redis = new IORedis(process.env.REDIS_URL)

// Cache-aside pattern: check cache first, fall back to DB, store result
async function getGymInfo(slug: string) {
  const cacheKey = `gym:${slug}`

  // 1. Check cache
  const cached = await redis.get(cacheKey)
  if (cached) return JSON.parse(cached)

  // 2. Cache miss — query DB
  const [gym] = await query('SELECT * FROM tenants WHERE slug = $1', [slug])
  if (!gym) return null

  // 3. Store in cache for 5 minutes
  await redis.setex(cacheKey, 300, JSON.stringify(gym))

  return gym
}

// Invalidate cache when gym settings change
async function updateGymSettings(slug: string, data: object) {
  await query('UPDATE tenants SET ... WHERE slug = $1', [slug])
  await redis.del(`gym:${slug}`)   // bust the cache
}

What to cache vs what not to

Cache thisDon't cache this
Gym settings / branding (changes rarely)Member data (changes on every payment/checkin)
Plan list (rarely changes)Payment status (must be real-time)
Expensive analytics queries (run once, cache result for 1h)User-specific data (different per user, hard to invalidate)
Static public data (gym info page)Anything security-sensitive

Authorisation — don't confuse with authentication

// Authentication = who are you? (JWT verification)
// Authorisation  = what are you allowed to do?

// Role-based guard middleware
function requireRole(...roles: string[]) {
  return (req, res, next) => {
    if (!roles.includes(req.user?.role)) {
      return res.status(403).json({ error: 'Forbidden — insufficient role' })
    }
    next()
  }
}

// Only owners can delete members
router.delete('/members/:id', requireAuth, requireRole('owner'), deleteMember)

// Resource-level check — even authenticated users must own the resource
async function getMember(req, res) {
  const [member] = await query(
    'SELECT * FROM members WHERE id = $1', [req.params.id]
  )
  // Check the member belongs to the caller's tenant
  if (member.tenant_id !== req.user.tenantId) {
    return res.status(404).json({ error: 'Not found' })
    // Return 404, not 403 — don't leak that the record exists
  }
  res.json({ member })
}

Architecture Patterns

How to structure a backend as it grows — from monolith to services.

Layered architecture (what this project uses)

Routes layer — HTTP: parse req, validate, call service, send res ↓ Service layer — Business logic: orchestrate DB calls, external APIs ↓ Data layer — DB queries, no business logic here ↓ Database — PostgreSQL: single source of truth 
// routes/members.ts — only HTTP concerns
router.post('/members', validate(schema), async (req, res, next) => {
  try {
    const member = await memberService.create(req.body, req.tenant.id)
    res.status(201).json({ member })
  } catch (err) { next(err) }
})

// services/member.service.ts — business logic
export const memberService = {
  async create(data, tenantId) {
    const existing = await memberRepo.findByEmail(data.email, tenantId)
    if (existing) throw new ConflictError('Email already registered')
    const member = await memberRepo.create(data, tenantId)
    await emailQueue.add('welcome', { to: member.email, name: member.name })
    return member
  }
}

// repositories/member.repo.ts — data access only
export const memberRepo = {
  findByEmail: (email, tenantId) =>
    query('SELECT * FROM members WHERE email=$1 AND tenant_id=$2', [email, tenantId]),
  create: (data, tenantId) =>
    query('INSERT INTO members (name, email, tenant_id) VALUES ($1,$2,$3) RETURNING *',
          [data.name, data.email, tenantId])
}

Multi-tenant architecture (how Myfiti works)

Single API server handles ALL gyms Each gym has its own PostgreSQL schema: tenant_korafit.members tenant_korafit.subscriptions tenant_gymx.members tenant_gymx.subscriptions Global schema holds cross-tenant data: public.tenants (gym name, slug, settings) public.owners (login credentials) Tenant middleware reads X-Tenant-Slug header → looks up tenant in public.tenants → sets search_path to tenant_korafit → all queries now hit that gym's data only
