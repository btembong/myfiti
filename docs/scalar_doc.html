Myfiti API — Beginner to Pro

A complete guide to using the Scalar API docs. Whether you've never touched an API before or you're building integrations, this guide has you covered.

Beginner
Beginner

What is an API?

Start here if you've never worked with an API before.

An API (Application Programming Interface) is how two software systems talk to each other. Think of it like a waiter in a restaurant — you (the client) tell the waiter (the API) what you want, the waiter goes to the kitchen (the server), and brings back the result.

The Myfiti API is how the web app, the mobile app, and the kiosk all talk to the database. Instead of each app writing its own database queries, they all call the same API.

HTTP Methods — the "verb" of a request

Every API call uses one of these verbs to describe what action you want:

MethodMeaningExample use
GETRead dataGet a list of members
POSTCreate something newCreate a member, send a login OTP
PATCHUpdate part of somethingUpdate a member's phone number
PUTReplace something entirelyReplace day-pass pricing config
DELETERemove somethingDelete a member or staff user

What is a URL / endpoint?

An endpoint is the address you send a request to. It's made of a base URL plus a path. For example: 

// Base URL
https://api.myfiti.fit

// Full endpoint — get all members
GET  https://api.myfiti.fit/api/members

// Full endpoint — get one specific member by ID
GET  https://api.myfiti.fit/api/members/b8160866-985c-4e78-8fda-d1b979a4ed3e

The part after the base URL (like /api/members) is called the path. Some paths have parameters in them (like :id) — you replace these with real values.

What is Scalar?

The tool you'll use to read and test the API.

Scalar is an interactive API documentation viewer. Instead of just describing what the API does, it lets you fill in fields and press Send to actually call the API — right from your browser, no code required.

Think of it like a control panel for the entire Myfiti API. Everything is organized, searchable, and testable.

https://api.myfiti.fit/api/docs Open Now →

The Scalar interface — 3 main areas

AreaWhat it does
Left sidebarLists all endpoints grouped by category. Click any to jump to it.
Center panelShows the endpoint description, request fields, and example responses.
Right panelThe "try it" panel — fill in values and send real requests.

Reading Responses

Understanding what the API sends back.

All responses are JSON (JavaScript Object Notation). It's a text format that looks like this:

// A single object
{
  "name":   "BEJUMEH BLAISE",
  "email":  "btb@shibmats.cm",
  "status": "active",
  "wallet_balance": 5000
}

// An array (list) of objects
{
  "members": [
    { "name": "Alice", "status": "active" },
    { "name": "Bob",   "status": "expired" }
  ],
  "total": 2
}

Key JSON types

TypeExampleMeaning
string"active"Text — always in double quotes
number5000A number — no quotes
booleantrue / falseYes or no
nullnullNothing / empty value
object{ "key": "value" }A group of key-value pairs in curly braces
array[ item1, item2 ]A list of items in square brackets
Beginner

HTTP Status Codes

The number that tells you whether the request worked.

Every response has a status code — a 3-digit number. You'll see it in Scalar next to the response. Here are the ones you'll encounter:

200
OK — request succeeded, data returned
201
Created — something new was created (member, payment, etc.)
400
Bad Request — you sent invalid data (check the error message in the response)
401
Unauthorized — you need a valid token (or the token expired)
403
Forbidden — your role doesn't have permission for this action
404
Not Found — the resource (member, subscription, etc.) doesn't exist
409
Conflict — already exists (e.g. email already registered)
429
Too Many Requests — rate limit hit, wait before retrying
500
Server Error — something broke on the server (not your fault)
502
Bad Gateway — upstream service (e.g. Tranzak) failed to respond
💡
Rule of thumb

2xx = success. 4xx = your problem (check what you sent). 5xx = server's problem.

Authentication

How to log in and get a token for protected endpoints.

Most endpoints require a JWT (JSON Web Token) — a long string that proves who you are. You get it by logging in, and then send it with every request in the Authorization header.

Step 1 — Call the login endpoint

In Scalar: Auth → POST /auth/login

// Request body
{
  "email":    "owner@korafit.cm",
  "password": "yourpassword"
}

// Response — copy the "token" value
{
  "token":  "eyJhbGciOiJIUzI1NiIsInR5...",
  "tenant": { "slug": "korafit", "name": "Kora Fit" },
  "user":   { "email": "owner@korafit.cm", "role": "owner" }
}

Step 2 — Set the token in Scalar

1

Click the 🔐 button

Top-right corner of Scalar — it's the Authenticate button.

2

Paste under BearerAuth

You'll see a field labelled BearerAuth. Paste the token value (not the full JSON — just the token string). Click Save.

3

Done — Scalar adds it automatically

From now on, every request you send from Scalar will include Authorization: Bearer <your-token> automatically.

Token types

Token typeLogin endpointWho it's for
Owner/StaffPOST /auth/loginGym owner, admin, receptionist, trainer
MemberPOST /auth/member/verify-otpGym members (mobile app)
SuperAdminPOST /superadmin/loginPlatform administrator
⚠️
Tokens expire

If you get a 401 after a while, your token has expired. Just log in again and set the new token.

Required Headers

Extra metadata you must send with most admin requests.

Headers are key-value pairs sent alongside a request — they carry metadata that the server needs. The Myfiti API requires two headers for most admin endpoints:

HeaderValueRequired for
AuthorizationBearer <token>All authenticated endpoints — Scalar sets this automatically after you authenticate
X-Tenant-SlugkorafitAll admin endpoints — tells the API which gym's data to use
Content-Typeapplication/jsonAny POST/PATCH request with a body — Scalar sets this automatically

How to set X-Tenant-Slug in Scalar

When you open an admin endpoint in Scalar, look for the Headers section in the right panel. Add:

X-Tenant-Slug: korafit
✅
Set it once per session

Scalar remembers your headers for the session. Set X-Tenant-Slug once and it stays for all subsequent requests.

Request Bodies

How to send data to POST and PATCH endpoints.

POST and PATCH requests usually need a request body — JSON data you send describing what you want to create or update. In Scalar, there's a Body section in the right panel with fields to fill in.

Example — Creating a member

Endpoint: POST/members

// Required fields (marked with * in Scalar)
{
  "name":  "Alice Mbah",
  "email": "alice@example.com"
}

// With optional fields
{
  "name":           "Alice Mbah",
  "email":          "alice@example.com",
  "phone":          "237655000000",
  "gender":         "female",
  "plan_id":        "uuid-of-the-plan",
  "payment_method": "cash"
}

Fields marked as required vs optional

In the Scalar center panel, the schema shows which fields are required (you must include them) and which are optional. If you miss a required field, you'll get a 400 Bad Request response.

Enum fields — only specific values allowed

Some fields only accept specific values. Scalar shows these as a dropdown. Examples:

FieldAllowed values
payment_method"cash" "mobile_money" "wallet"
gender"male" "female" "other"
status"active" "suspended" "expired"
role (staff)"admin" "receptionist" "trainer"

Query Parameters & Filters

How to filter, search, and paginate results on GET endpoints.

GET endpoints often accept query parameters — optional filters you append to the URL using ?key=value. In Scalar, these appear as fields in the Query section. 

// Get only active members
GET /api/members?status=active

// Search by name
GET /api/members?search=alice

// Combine filters — page 2, 10 per page, active only
GET /api/members?status=active&page=2&limit=10

// Revenue report for a date range
GET /api/analytics/revenue?from=2026-09-01&to=2026-09-30

Common query params across endpoints

ParamTypeDescription
searchstringFree-text search on name, email, phone
statusstringFilter by status (active, expired, pending...)
pageintegerPage number (default: 1)
limitintegerItems per page (default: 20)
fromdate (YYYY-MM-DD)Start of date range
todate (YYYY-MM-DD)End of date range
member_iduuidFilter by a specific member

Understanding and Handling Errors

What to do when something goes wrong.

All error responses have the same shape:

{
  "error": "Member not found."
}

Common errors and what to do

ErrorCauseFix
401 UnauthorizedNo token, wrong token, or expired tokenLog in again and set the new token in Scalar
403 ForbiddenYour role doesn't have accessUse an owner or admin token instead of a receptionist/member token
400 Bad RequestMissing required field, wrong type, invalid enum valueCheck the request body — look at the schema in the center panel for what's required
404 Not FoundThe ID in the URL doesn't existVerify the ID you copied — it might be from a different gym's data
409 ConflictEmail already registeredUse a different email for testing, or look up the existing member
429 Too Many RequestsHit the rate limit (login/OTP endpoints)Wait 60 seconds and try again
502 Bad GatewayTranzak API not responding, or wrong field names sentCheck Tranzak credentials in server .env — or check for field naming issues
💡
Always read the error message

The "error" field in the response body usually tells you exactly what went wrong. Read it before debugging further.

Chaining Requests

Using the output of one request as the input for the next.

Real workflows require multiple API calls in sequence — the output of one becomes the input for the next. This is called request chaining. Scalar doesn't automate this, so you copy values manually.

Example — Full member onboarding chain

── Step 1: Get plan IDs ──────────────────────────────────────
GET /public/gym/korafit/plans
→ Response: [ { "id": "plan-uuid-1", "name": "Monthly", "price": 10000 } ]
→ Copy:     plan-uuid-1

── Step 2: Create the member ─────────────────────────────────
POST /members
Body: { "name": "Test User", "email": "test@example.cm", "plan_id": "plan-uuid-1" }
→ Response: { "member": { "id": "member-uuid-1", "status": "pending" } }
→ Copy:     member-uuid-1

── Step 3: Confirm payment ───────────────────────────────────
POST /members/member-uuid-1/confirm-payment
Body: { "payment_method": "cash" }
→ Response: { "ok": true }  — member is now active

── Step 4: Verify the member is active ───────────────────────
GET  /members/member-uuid-1
→ Response: { "member": { "status": "active", "expires_at": "2026-10-30..." } }

Keeping track — use a notepad

During testing, keep a plain text file or browser tab open to paste UUIDs you collect. You'll typically need: plan_id, member_id, payment_id, subscription_id.

Payment Flow Testing

Testing wallet, mobile money, and cash payment paths end-to-end.

🔴
This is the live production API

Mobile money tests trigger real Tranzak USSD pushes to real phone numbers. Wallet tests deduct real balances. Always use test accounts with small amounts.

Path 1 — Cash renewal (safest to test)

POST /public/gym/korafit/renew
{
  "member_id":      "b8160866-985c-4e78-8fda-d1b979a4ed3e",
  "plan_id":        "your-plan-uuid",
  "payment_method": "cash"
}

// Response — member gives this code to receptionist
{
  "ok":        true,
  "method":    "cash",
  "reference": "CASH-A3F8",
  "amount":    10000,
  "currency":  "XAF"
}

Path 2 — Wallet renewal (OTP required)

── Step 1: Send OTP to member's email ───────────────────────
POST /public/gym/korafit/send-otp
{ "member_id": "b8160866-..." }
→ { "ok": true, "sent_to": "bt****@shibmats.cm" }
→ Check the email inbox for the 6-digit code

── Step 2: Verify OTP ───────────────────────────────────────
POST /public/gym/korafit/verify-otp
{ "member_id": "b8160866-...", "code": "482931" }
→ { "ok": true }

── Step 3: Renew with wallet ────────────────────────────────
POST /public/gym/korafit/renew
{ "member_id": "b8160866-...", "plan_id": "...", "payment_method": "wallet", "otp_code": "482931" }
→ { "ok": true, "method": "wallet", "expires_at": "2026-10-30T..." }

Path 3 — Mobile money renewal (Tranzak redirect)

── Step 1: Initiate ─────────────────────────────────────────
POST /public/gym/korafit/renew
{ "member_id": "...", "plan_id": "...", "payment_method": "mobile_money" }
→ { "ok": true, "payment_url": "https://pay.tranzak.me/...", "payment_id": "TZ-abc..." }
→ Open payment_url in browser → complete the Tranzak payment flow

── Step 2: Poll status after completing payment ──────────────
GET  /public/gym/korafit/payment-status?pid=TZ-abc...&mid=member-uuid
→ { "status": "successful", "expires_at": "2026-10-30T..." }

In-app mobile money (USSD push — mobile app flow)

// Member is logged in — uses /member/me/renew instead
POST /member/me/renew
{
  "plan_id":        "...",
  "payment_method": "mobile_money",
  "phone":          "237655123456"
}
→ { "ok": true, "payment_id": "pay-uuid..." }
→ Member approves USSD push on their phone

// Poll until status = completed
GET  /member/me/payment/pay-uuid...
→ { "status": "completed" }  — subscription now active

Webhook Testing

How Tranzak notifies the API when payments complete.

Webhooks are server-to-server callbacks. After a Tranzak payment succeeds, Tranzak sends a POST request to /api/webhooks/tranzak automatically. You don't trigger this from Scalar.

Webhook flow

1. Member initiates payment → API creates pending subscription
2. Member completes payment on Tranzak (USSD or hosted page)
3. Tranzak calls: POST /api/webhooks/tranzak?ctx=public-renew&tenant=korafit&id=sub-uuid
4. API verifies HMAC signature, finds pending subscription, sets status=active
5. API updates member status=active
6. Done — member is renewed, no polling needed

Checking webhook delivery in logs

On the VPS, you can see incoming webhooks in the API logs:

// SSH into the VPS and watch live logs
pm2 logs api --lines 0

// Then trigger a payment — you'll see
POST /api/webhooks/tranzak?ctx=public-renew&tenant=korafit&id=... 200 42ms

Testing webhooks locally (ngrok)

To test webhooks on your local machine, use ngrok to create a public tunnel to localhost:

// Install ngrok, then expose your local API
ngrok http 4000

// ngrok gives you a public URL like:
https://a1b2c3.ngrok.io

// Use this as the callbackUrl in Tranzak payment requests
callbackUrl: "https://a1b2c3.ngrok.io/api/webhooks/tranzak?ctx=..."

Pro Tips

🔍
Search is your fastest navigation

In Scalar, type the endpoint name or keyword in the search box. You'll jump there in one keystroke instead of scrolling through the sidebar.

📋
Copy as curl from Scalar

After filling in a request, Scalar shows the equivalent curl command. Copy it to share the exact call with a teammate or paste it in your terminal.

🔑
Keep a token bank

Keep a notepad with your current tokens for each role: owner token, member token, superadmin token. Swap them in Scalar when you need to test different permissions.

🧪
Always test the unhappy path

After a successful request, try breaking it — send a wrong ID, missing field, or wrong enum value. Verify you get the right error code and message. This is how you know the API is properly validated.

📦
Use Postman environments for different stages

Create two Postman environments: Local (baseUrl = http://localhost:4000/api) and Production (baseUrl = https://api.myfiti.fit/api). Switch between them with one click.

⚠️
Production data is real

Scalar hits the live API. Don't DELETE real members, don't PATCH real subscriptions unless you mean it. For destructive testing, create a throwaway member first.
