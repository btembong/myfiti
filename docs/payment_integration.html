What is Payment Integration?

How software applications collect money — without handling cash or banking directly.

A payment integration is how your application connects to an external service that processes real money transactions. Instead of building your own banking infrastructure (which requires licenses, compliance, and years of work), you call a payment provider's API and they handle the actual movement of money.

Think of it this way:

Your app doesThe payment provider does
Tells the provider "charge XAF 10,000 to this phone number"Connects to mobile money network, triggers USSD prompt, waits for approval
Records the payment reference and waits for confirmationDeducts from payer's account, deposits to merchant account
Updates the member's subscription when confirmedSends a webhook callback with the result

Why not just accept cash?

You can — and Myfiti supports cash payments too. But digital payments add:

BenefitHow it works
Remote paymentMember pays from their phone at home, subscription activates automatically
No manual confirmationWebhook arrives → subscription activated, no staff needed
Audit trailEvery transaction has a reference ID, timestamp, and status — no disputes
Partial automationRenewal reminders + payment links sent by email → self-service
💡
Payment provider = payment gateway

Payment provider, payment gateway, and payment processor are often used interchangeably. They all mean the same thing: the service that sits between your app and the banking network. Tranzak is ours for Cameroon/Central Africa mobile money.

Payment Flow Types

There are three fundamentally different ways a payment can happen — understanding these eliminates most integration confusion.

Type 1 — Hosted Payment Page (Redirect)

Your app sends the customer to the provider's payment page. The provider handles the UI. When done, the customer comes back to your site.

Customer → clicks "Pay Now" on your site
Your app → calls provider API → gets a payment URL
Your app → redirects customer to payment URL
Customer → fills card details / selects mobile money on provider's page
Provider → processes payment
Provider → calls YOUR webhook URL with result (server-to-server)
Provider → redirects customer back to your returnUrl

Used in Myfiti for: Web renewal page (/member/renew) when payment_method = mobile_money

Tranzak endpoint: POST /xp021/v1/request/create

Type 2 — Direct Charge / USSD Push

Your server charges the customer's phone directly — no redirect. The customer receives a USSD pop-up on their handset and approves by entering their PIN.

Customer → enters phone number in your app
Your app → calls provider API with amount + phone number
Provider → sends USSD prompt to customer's phone (like a *123# menu)
Customer → approves with their mobile money PIN
Provider → calls YOUR webhook URL with result
Your app → activates subscription on webhook receipt

Used in Myfiti for: Mobile app in-app renewal, mobile app wallet top-up

Tranzak endpoint: POST /xp021/v1/request/create-mobile-wallet-charge

Type 3 — Disbursement / Payout

Your server sends money to a customer's phone — the reverse of a charge. Used for refunds, cashouts, or prize payouts.

Your app → calls provider API with amount + recipient phone
Provider → deducts from YOUR merchant wallet
Provider → credits recipient's mobile money account
Provider → sends webhook confirming completion

Used in Myfiti for: Member wallet cashout

Tranzak endpoint: POST /xp021/v1/request/create-mobile-wallet-payout

Key Concepts

Seven terms that appear in every payment integration — understand these first.

TermWhat it meansExample
Transaction Reference A unique ID you generate to identify this payment attempt. Used to link the provider's result back to your database record. RENEW-b8160866-1725264000
Request ID A unique ID the provider assigns to your payment request. Use this to look up status. TZ-abc123def456
Webhook A POST request the provider sends to your server when a payment completes. This is how you know it worked — do NOT rely on the customer returning to your site. POST /api/webhooks/tranzak
callbackUrl The URL you give the provider so it knows where to send the webhook. https://api.myfiti.fit/api/webhooks/tranzak?ctx=renew&tenant=korafit&id=sub-uuid
returnUrl Where the customer's browser goes after they finish on the provider's hosted page. (Browser redirect — different from webhook.) https://app.myfiti.fit/payment/success
Idempotency Ensuring the same payment isn't processed twice even if your code calls the provider multiple times with the same reference. Use the same mchTransactionRef — provider returns the same result instead of charging twice
Pending → Successful Payments start as pending and transition to successful or failed. Never assume instant. USSD push can take 30 seconds to 5 minutes to complete
🔴
Never activate a subscription based on customer return to your site

The customer can close the browser, modify URLs, or arrive at returnUrl even if payment failed. Only activate subscriptions inside your webhook handler, after verifying the provider's signature.

Always develop against the sandbox — it behaves identically but moves no real money.

Switching between sandbox and live in Myfiti

The env var TRANZAK_ENV controls which base URL the code uses:

# apps/api/.env

# Sandbox (development)
TRANZAK_ENV=sandbox
TRANZAK_APP_ID=your-sandbox-app-id
TRANZAK_APP_KEY=your-sandbox-app-key

# Live (production) — set this on the VPS
TRANZAK_ENV=live
TRANZAK_APP_ID=your-live-app-id

⚠️
Sandbox webhooks need a public URL

Tranzak's sandbox still sends real HTTP POST requests to your callbackUrl. If you're developing locally, Tranzak cannot reach localhost:4000. Use ngrok to create a public tunnel: ngrok http 4000, then use the generated URL as your callbackUrl.

Your First API Call

Get an auth token from Tranzak — the first call every integration must make.

Before you can call any Tranzak endpoint, you need a Bearer token. You get it by POSTing your appId and appKey.

# Using curl — sandbox example
curl -X POST https://sandbox.dsapi.tranzak.me/auth/token \
  -H "Content-Type: application/json" \
  -d '{"appId":"YOUR_APP_ID","appKey":"YOUR_APP_KEY"}'

# Response
{
  "data": {
    "token":     "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...",
    "expiresAt": "2026-09-02T12:30:00Z"
  },
  "success": true
}

You then include this token in every subsequent call as a header:

Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...
💡
Tokens are short-lived

Tranzak tokens expire. In production code (see Authentication section), you should fetch a fresh token before each request rather than caching one for hours. Myfiti's tranzak.ts does this automatically by calling getAuthToken() at the start of every tranzakFetch() call.

Authentication Deep Dive

How Tranzak auth works under the hood and how Myfiti implements it.

Tranzak uses a two-step auth model: your appId/appKey are long-lived credentials; the token they generate is short-lived (expires in ~1 hour).

Auth flow

Your server → POST /auth/token { appId, appKey }
Tranzak → { data: { token, expiresAt } }
Your server → POST /xp021/v1/... Authorization: Bearer <token>
Tranzak → { data: {...}, success: true }

Myfiti's implementation

The getAuthToken() function in apps/api/src/lib/tranzak.ts fetches a fresh token on every call — no caching:

// apps/api/src/lib/tranzak.ts — simplified
async function getAuthToken(appId, appKey) {
  const res = await fetch(`${BASE_URL}/auth/token`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ appId, appKey }),
  })

  const body = await res.json()
  // Supports both { data: { token } } and { token } response shapes
  const token = body.data?.token ?? body.token
  if (!token) throw new Error(`Tranzak auth error: ${JSON.stringify(body)}`)
  return token
}

// Then every API call goes through tranzakFetch() which auto-fetches a token
async function tranzakFetch(path, options) {
  const token = await getAuthToken()
  return fetch(BASE_URL + path, {
    ...options,
    headers: { 'Authorization': `Bearer ${token}`, ...options.headers },
  })
}
✅
Per-request auth is the safest pattern

Fetching a fresh token per request adds ~100ms latency but eliminates all "expired token" errors. For high-volume systems you'd cache with a short TTL (e.g. 55 minutes), but for a gym management API this is unnecessary complexity.

Webhooks — Payment Notifications

How Tranzak tells your server that a payment completed — the most critical part of any integration.

When a payment completes (success or failure), Tranzak sends a POST request to your callbackUrl. This is called a webhook. Your server must receive it, verify it, and act on it.

Webhook payload structure

// POST /api/webhooks/tranzak?ctx=public-renew&tenant=korafit&id=sub-uuid
{
  "eventType":  "REQUEST.COMPLETED",
  "resourceId": "TZ-abc123def456",
  "authKey":    "your-webhook-secret-string",
  "resource": {
    "requestId":        "TZ-abc123def456",
    "mchTransactionRef": "RENEW-b8160866-1725264000",
    "status":           "SUCCESSFUL",
    "amount":           10000,
    "currencyCode":     "XAF",
    "transactionTime":  "2026-09-02T09:15:32Z"
  }
}

All possible status values

StatusMeaningAction
SUCCESSFULPayment approved and funds transferredActivate subscription / fulfill order
FAILEDPayment declined or error occurredMark payment as failed, notify user
CANCELLEDCustomer cancelled on payment pageMark as cancelled, prompt to retry
CANCELLED_BY_PAYERCustomer rejected USSD promptMark as cancelled, prompt to retry
PENDINGAwaiting customer actionNo action yet — wait for next webhook
PAYMENT_IN_PROGRESSUSSD sent, awaiting customer PINNo action yet
PAYER_REDIRECT_REQUIREDAwaiting redirect completionNo action yet

What your webhook handler must do

1

Verify the authKey

Check that payload.authKey matches your stored TRANZAK_WEBHOOK_SECRET. Reject with 401 if it doesn't.

2

Check for duplicates

Look up resource.mchTransactionRef in your database. If already processed, return 200 immediately (don't process twice).

3

Only act on SUCCESSFUL

If resource.status !== 'SUCCESSFUL', log it but return 200 without activating anything.

4

Fulfill the order

Using the context from query params (?ctx=, &tenant=, &id=), find the pending subscription and activate it.

5

Respond 200 quickly

Return { ok: true } within 10 seconds. If you take longer, Tranzak may retry. Do heavy processing asynchronously after responding.

Webhook Security

How to verify that a webhook really came from Tranzak and not a malicious actor.

Anyone who discovers your webhook URL could POST fake payment notifications to it. This is why Tranzak sends an authKey field inside every webhook payload. You verify it against your stored webhook secret.

How Tranzak's authKey works

Unlike some providers (Stripe uses HMAC-SHA256 on the raw body), Tranzak uses a simpler approach:

  • You configure a webhook secret in your Tranzak dashboard
  • Tranzak includes that exact string as authKey in every webhook payload
  • You compare payload.authKey to your stored secret using a timing-safe comparison

Myfiti's implementation

// apps/api/src/routes/webhooks.ts
import crypto from 'crypto'

function verifyTranzakAuthKey(authKey, secret) {
  if (!authKey) return false
  try {
    // timingSafeEqual prevents timing attacks — always use this for secret comparison
    return crypto.timingSafeEqual(
      Buffer.from(authKey),
      Buffer.from(secret)
    )
  } catch {
    return false  // length mismatch throws — treat as invalid
  }
}

// In the webhook handler:
if (!verifyTranzakAuthKey(payload.authKey, webhookSecret)) {
  return res.status(401).json({ error: 'invalid_authKey' })
}

Why timing-safe comparison?

A regular === string comparison stops as soon as it finds a mismatch — this leaks information about how many characters were correct (timing attack). crypto.timingSafeEqual always takes the same time regardless of where the mismatch is.

How other providers do security

ProviderMethodWhat you check
TranzakauthKey in bodypayload.authKey === WEBHOOK_SECRET
StripeHMAC-SHA256 signature headerstripe-signature header — reconstructed from raw body
FlutterwaveSecret hash headerverif-hash header === your secret
MTN MoMoOAuth 2.0 + callback auth tokenBearer token in callback Authorization header
⚠️
Use raw body for HMAC-based providers

For Stripe and similar providers, you must read the raw request body (not parsed JSON) to verify the signature — because JSON parsing can reorder fields and break the HMAC. In Express: app.use('/webhooks/stripe', express.raw({ type: 'application/json' }))

When webhooks aren't guaranteed — how to actively check payment status.

Webhooks can occasionally fail (network issue, your server was down briefly). Polling is a fallback — you periodically call the provider's status endpoint until the payment resolves.

Idempotency

Preventing double-charges when network errors cause your code to retry.

Idempotency means: calling the same operation twice produces the same result as calling it once. For payments this is critical — a network timeout on your server doesn't mean the payment failed; Tranzak may have already charged the customer.

The problem

Your server → POST /xp021/v1/request/create { mchTransactionRef: "RENEW-123" }
Tranzak → creates payment, sends USSD...
Network → timeout! Your server never gets the response
Your server → retries: POST /xp021/v1/request/create { mchTransactionRef: "RENEW-123" }
Tranzak → recognises same mchTransactionRef → returns existing request, no double charge

How mchTransactionRef prevents double charges

If you send the same mchTransactionRef twice, Tranzak returns the existing payment request instead of creating a new one. This is the idempotency key.

How to construct a good reference

// Pattern: ACTION-ENTITY_ID-TIMESTAMP
"RENEW-b8160866-1725264000"      // subscription renewal for member
"TOPUP-b8160866-1725264100"      // wallet top-up
"DAYPASS-korafit-1725264200"     // day pass purchase
"CASHOUT-b8160866-1725264300"   // wallet cashout

// In Node.js:
const ref = `RENEW-${member.id}-${Math.floor(Date.now() / 1000)}`
⚠️
Don't reuse references for retry attempts

If a payment genuinely failed and the customer wants to try again, generate a NEW reference. Reusing the old one would return the failed payment status instead of initiating a new charge.

Important differences from a charge

Charge (collect)Payout (disburse)

When processing a cashout: (1) deduct the amount from the member's wallet balance in your DB, (2) then call Tranzak. If you call Tranzak first and your server crashes before updating the DB, the money leaves your account but the member's balance isn't reduced — they could request it again.

Full Integration Pattern

The correct end-to-end architecture for any payment feature — from initiation to database update.

The complete flow (hosted payment example)

── 1. User clicks "Pay" ──────────────────────────────────────
   POST /api/public/gym/korafit/renew
   { member_id, plan_id, payment_method: "mobile_money" }

── 2. Your API creates a pending record ──────────────────────
   INSERT INTO subscriptions (status='pending', ...)    ← save BEFORE calling provider
   INSERT INTO payments      (status='pending', ...)

── 3. Your API calls Tranzak ─────────────────────────────────
   POST /xp021/v1/request/create
   { amount, mchTransactionRef: "RENEW-uuid-ts", callbackUrl: "...?ctx=public-renew&id=sub-uuid" }

── 4. Store the requestId ────────────────────────────────────
   UPDATE payments SET tranzak_request_id='TZ-abc' WHERE id=pay-uuid

── 5. Return payment URL to client ───────────────────────────
   { ok: true, payment_url: "https://pay.tranzak.me/...", payment_id: "TZ-abc" }

── 6. Client redirects user ──────────────────────────────────
   window.location.href = payment_url

── 7. User completes payment on Tranzak ──────────────────────
   (separate — user on Tranzak's site)

── 8. Tranzak calls your webhook ─────────────────────────────
   POST /api/webhooks/tranzak?ctx=public-renew&tenant=korafit&id=sub-uuid
   { authKey: "...", resource: { status: "SUCCESSFUL", mchTransactionRef: "RENEW-uuid-ts" } }

── 9. Webhook handler: verify, dedupe, activate ──────────────
   verifyAuthKey(payload.authKey, secret)    → 401 if invalid
   check webhook_events for duplicate        → 200 if seen before
   if status !== "SUCCESSFUL" → 200 + ignore
   UPDATE subscriptions SET status='active', expires_at=...
   UPDATE members      SET status='active'
   UPDATE payments     SET status='completed', paid_at=...
   INSERT INTO webhook_events (status='processed')

── 10. Respond 200 to Tranzak ────────────────────────────────
    { ok: true }

Key architectural rules

  • Create the DB record before calling the provider — if the provider call fails, you have a pending record to retry from
  • Store requestId from Tranzak immediately — you'll need it for status polling
  • All state changes happen only in the webhook handler — never in the returnUrl handler
  • Use context in callbackUrl query params — embed tenant, entity ID, and context type so the webhook handler knows what to activate
  • Respond 200 fast — do DB writes synchronously but skip anything slow (emails, push notifications) until after responding

A complete, production-ready Tranzak client in TypeScript — based on Myfiti's actual code.

The Tranzak client

// lib/tranzak.ts
const BASE_URL = process.env.TRANZAK_ENV === 'live'
  ? 'https://dsapi.tranzak.me'
  : 'https://sandbox.dsapi.tranzak.me'

/** Fetch a short-lived auth token */
async function getToken() {
  const res = await fetch(`${BASE_URL}/auth/token`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      appId:  process.env.TRANZAK_APP_ID,
      appKey: process.env.TRANZAK_APP_KEY,
    }),
  })
  const body = await res.json()
  const token = body.data?.token ?? body.token
  if (!token) throw new Error(`Tranzak auth failed: ${JSON.stringify(body)}`)
  return token
}

/** Authenticated fetch to any Tranzak endpoint */
async function tranzakFetch<T>(path: string, options: RequestInit = {}): Promise<T> {
  const token = await getToken()
  const res = await fetch(BASE_URL + path, {
    ...options,
    headers: {
      'Content-Type':  'application/json',
      'Authorization': `Bearer ${token}`,
      ...options.headers,
    },
  })
  if (!res.ok) {
    const err = await res.text()
    throw new Error(`Tranzak [${res.status}]: ${err}`)
  }
  return res.json()
}

/** Create a hosted payment request */
export async function createPayment({ amount, currency, reference, callbackUrl, returnUrl }) {
  const body = await tranzakFetch<{
    data: { requestId: string; links: { paymentAuthUrl: string } }
    success: boolean
  }>('/xp021/v1/request/create', {
    method: 'POST',
    body: JSON.stringify({
      amount,
      currencyCode:       currency,
      mchTransactionRef:  reference,   // NOT merchantTransactionId
      callbackUrl,
      returnUrl,
      description: `Payment ref: ${reference}`,
    }),
  })
  if (!body.success) throw new Error('Tranzak create failed')
  return {
    requestId:  body.data.requestId,
    paymentUrl: body.data.links.paymentAuthUrl,  // NOT data.paymentUrl
  }
}

  }>('/xp021/v1/request/create-mobile-wallet-charge', {

/** Poll payment status */
export async function getStatus(requestId: string) {
  const statusMap = {
    SUCCESSFUL:           'successful',
    FAILED:               'failed',
    CANCELLED:            'failed',
    CANCELLED_BY_PAYER:   'failed',
    PENDING:              'pending',
    PAYMENT_IN_PROGRESS:  'pending',
    PAYER_REDIRECT_REQUIRED: 'pending',
  }

  const body = await tranzakFetch<{ data: { status: string; amount: number } }>(
    `/xp021/v1/request/details?requestId=${requestId}`
  )

  return statusMap[body.data.status] ?? 'pending'
}

Production Webhook Handler

A complete, safe webhook handler — based on Myfiti's actual implementation.

// routes/webhooks.ts — simplified but production-accurate
import crypto from 'node:crypto'
import { Router } from 'express'

const router = Router()

// IMPORTANT: webhook route must use raw body parser for signature verification
// (even though Tranzak uses authKey, not HMAC — good practice to keep raw)
// app.use('/webhooks', express.raw({ type: 'application/json' }))

router.post('/tranzak', async (req, res) => {
  // 1. Parse body
  let payload
  try {
    payload = typeof req.body === 'string'
      ? JSON.parse(req.body)
      : req.body
  } catch {
    return res.status(400).json({ error: 'invalid_json' })
  }

  const resource = payload.resource
  if (!resource) return res.status(400).json({ error: 'missing_resource' })

  const { mchTransactionRef, status, amount, currencyCode, transactionTime } = resource
  if (!mchTransactionRef) return res.status(400).json({ error: 'missing_ref' })

  // 2. Read context from callbackUrl query params
  const ctx    = req.query.ctx    // e.g. "public-renew"
  const tenant = req.query.tenant // e.g. "korafit"
  const id     = req.query.id     // e.g. subscription UUID

  // 3. Verify authKey
  const secret = process.env.TRANZAK_WEBHOOK_SECRET
  if (!secret || !timingSafeEqual(payload.authKey, secret)) {
    return res.status(401).json({ error: 'invalid_authKey' })
  }

  // 4. Deduplicate — check if we've already processed this reference
  const existing = await db.query(
    'SELECT id FROM webhook_events WHERE transaction_ref = $1 AND status = $2',
    [mchTransactionRef, 'processed']
  )
  if (existing.rows.length > 0) {
    return res.status(200).json({ ok: true, duplicate: true })
  }

  // 5. Only act on successful payments
  if (status !== 'SUCCESSFUL') {
    return res.status(200).json({ ok: true, ignored: status })
  }

  // 6. Activate subscription based on context
  await activateSubscription({ id, tenant, amount, currencyCode, transactionTime, mchTransactionRef })

  // 7. Respond immediately — emails/notifications happen after
  res.status(200).json({ ok: true })
})

function timingSafeEqual(a, b) {
  if (!a || !b) return false
  try {
    return crypto.timingSafeEqual(Buffer.from(a), Buffer.from(b))
  } catch { return false }
}

Security Checklist

Every item here represents a real attack vector if ignored.

CheckWhy it mattersStatus in Myfiti
Verify webhook signature on every request Anyone can POST to your webhook URL and fake a payment confirmation Done — timingSafeEqual(authKey, secret)
Use timing-safe comparison Normal string comparison leaks secret length via timing Done — crypto.timingSafeEqual
Deduplicate webhook events Webhook retries can double-activate subscriptions if not handled Done — webhook_events table
Store credentials in env, not code Keys committed to git can never be fully revoked Done — .env + VPS env
Never log full API keys or tokens Log aggregators may store them indefinitely Done — only log refs/IDs
Validate amount before activating Attacker could replay a payment for XAF 1 to activate a XAF 10,000 plan Partial — verify amount in webhook handler
HTTPS only for callbackUrl HTTP webhooks can be intercepted and the authKey stolen Done — all URLs use https://
Rate limit payment initiation endpoints Attacker could flood provider with fake payment requests Done — rateLimitApi middleware
⚠️
Amount validation is important

When your webhook fires, verify that the amount in resource.amount matches what the subscription should cost. A sophisticated attacker could initiate a payment for XAF 1, get a webhook, and replay it against a different subscription endpoint.

Common Bugs (Real Examples)

Actual bugs from Myfiti's production integration — with root cause and fix.

Bug 1 — Wrong field name causes 502

// WRONG — field name doesn't exist in Tranzak's API
body: JSON.stringify({
  merchantTransactionId: reference,   // ← invalid field
})

// CORRECT
body: JSON.stringify({
  mchTransactionRef: reference,       // ← correct field name
})

Symptom: POST /api/public/gym/korafit/renew returns 502. PM2 logs show Tranzak returning 400.

Root cause: Assumed field name without checking the actual API spec.

Prevention: Always test against the real API (not docs alone) and log the raw Tranzak error response.

Bug 2 — Wrong response path crashes the server

// WRONG — data.paymentUrl doesn't exist
const paymentUrl = paymentData?.data?.paymentUrl ?? ''  // ← undefined

// CORRECT — the URL is nested inside links
const paymentUrl = paymentData?.data?.links?.paymentAuthUrl ?? ''  // ← correct

Symptom: Payment URL returned to client is an empty string — Tranzak redirect page shows "invalid link".

Root cause: Assumed response structure without verifying against actual response.

Prevention: Log the full Tranzak response during development. Write the actual type definition from real responses.

Bug 3 — Activating subscription on browser return (not webhook)

// WRONG — user's browser arrives at returnUrl
app.get('/payment/success', async (req, res) => {
  const { ref } = req.query
  await activateSubscription(ref)  // ← NEVER do this
  res.send('Payment successful!')
})

// CORRECT — only activate inside the webhook handler
app.get('/payment/success', async (req, res) => {
  // Just show a "processing..." UI — poll status separately
  res.send('Processing your payment...')
})

Symptom: Subscriptions activated without actual payment — attacker crafts a returnUrl request manually.

Root cause: Treating the customer's browser return as proof of payment.

Bug 4 — Forgetting to save requestId

// WRONG — requestId discarded after create
const { paymentUrl } = await createPayment(...)
// requestId never stored — can't poll status later

// CORRECT
const { paymentUrl, requestId } = await createPayment(...)
await db.query(
  'UPDATE payments SET tranzak_request_id=$1 WHERE id=$2',
  [requestId, paymentId]
)

Symptom: Cannot reconcile failed webhooks — no way to poll status for pending payments.

How Myfiti's code isolates provider differences

The PaymentProviderClient interface in @gymflow/types defines two methods: initializeTransaction() and verifyTransaction(). The Tranzak implementation maps Tranzak-specific field names to this interface. Adding a new provider means writing a new implementation of the same interface — the rest of the codebase doesn't change. 

// @gymflow/types — the provider-agnostic interface
interface PaymentProviderClient {
  initializeTransaction(params: {
    amount:       number
    currency:     string
    reference:    string
    callback_url: string
    metadata?:    Record<string, unknown>
  }): Promise<{ payment_url: string; reference: string; request_id: string }>

  verifyTransaction(requestId: string): Promise<{
    reference: string
    status:    'pending' | 'successful' | 'failed'
    amount:    number
    currency:  string
    paid_at:   string | null
  }>
}

// Swap providers by changing one line:
import { tranzak } from './tranzak.js'    // current
import { stripe }  from './stripe.js'    // hypothetical future

const paymentProvider: PaymentProviderClient = tranzak  // change this one var
✅
Design against an interface, not a provider

The best payment integrations hide provider specifics behind a thin abstraction layer. Your business logic calls paymentProvider.initializeTransaction() — it doesn't know or care whether that calls Tranzak, Stripe, or Flutterwave underneath.
